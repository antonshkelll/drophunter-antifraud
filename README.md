# DropHunter

Модель, которая ищет дропперов: счета, через которые мошенники выводят деньги жертв. Признаки собираются на SQL, модель — градиентный бустинг, а порог выбирается не по ROC-AUC, а по деньгам с учётом того, сколько алертов успевает разобрать команда.

## Контекст

По данным Банка России, во II квартале 2026 года банки отразили 17,5 млн попыток хищений, но мошенники всё равно провели 458,7 тыс. операций примерно на 7,4 млрд ₽ ([Profile](https://profile.ru/?p=1887685)). Без дропперов украденное не обналичить. С 2024 года банк обязан вернуть клиенту деньги, если перевёл их на счёт из базы ФинЦЕРТ, а с 2025 года за дропперство есть уголовная ответственность. Число выявленных дроп-карт в 2026 году, по оценкам, может вырасти вдвое ([Финансы Mail](https://finance.mail.ru/article/chislo-vyiyavlennyih-kart-dropov-v-2026-godu-mozhet-vyirasti-vdvoe-69195108/)).

Для банка ошибка в обе стороны стоит денег: пропущенный дроппер означает возврат клиенту, ложная блокировка — звонок в поддержку и риск оттока.

## Постановка

Раз в два месяца модель оценивает всех клиентов с входящими переводами, и топ отправляется аналитикам на проверку.

- **Объект:** клиент за период. **Цель:** клиент был подтверждённым дроппером в этом периоде.
- **Валидация out-of-time:** обучение на апреле–мае, тест на июне–июле. Дропперы во втором периоде в основном новые, как и в жизни.
- **Ограничение:** команда разбирает 300 алертов за период.

```
Чистый эффект = предотвращённый ущерб − ложные блокировки × 2 100 ₽ − проверки × 150 ₽
                 (Recall@k)              (Precision@k)
```

При доле дропперов 0,6% ROC-AUC у любой разумной модели близок к единице и мало что говорит, поэтому основные метрики здесь PR-AUC, Precision/Recall@300 и рубли.

## Данные

Реальные транзакции — банковская тайна, поэтому [генератор](src/generate_data.py) создаёт синтетику по паттернам из открытых материалов ЦБ и банков: 40 000 клиентов, ~1,57 млн переводов и ~245 тыс. снятий наличных за 120 дней.

Чтобы задача не была игрушечной:

- дропперы двух типов: «простые» (быстрый вывод, круглые суммы) и «продвинутые» (держат деньги днями, выводят часть);
- есть клиенты, похожие на дропперов, но честные: самозанятые, P2P-трейдеры, студенты с переводами от родителей, продажи с рук;
- ~15% дропперов так и не подтверждаются и в данных выглядят обычными клиентами (шум в разметке).

Объём мошенничества завышен, чтобы модели было на чём учиться, поэтому абсолютные суммы в рублях условны. Смотреть стоит на сравнение моделей между собой.

## Признаки

Все признаки считаются одним запросом в DuckDB: [`sql/features.sql`](sql/features.sql). Скорость вывода денег («через сколько минут после входящего перевода было ближайшее списание») считается через `ASOF JOIN`. Запрос покрыт тестом на маленьком примере, где значения посчитаны вручную.

| Группа | Признаки |
|---|---|
| Профиль | возраст, стаж счёта, дни с последней смены телефона, число устройств, зарплатный клиент |
| Входящие | количество, сумма, уникальные отправители, доля новых отправителей, доля круглых сумм, ночные, отправители 55+, пик отправителей за день |
| Исходящие | сумма, доля наличных, доля во внешние банки, ночные |
| Транзит | pass-through (вывод / приход), медиана минут до вывода, доля вывода в течение часа |

## Результаты

Out-of-time тест: 39 963 клиента, 263 дроппера.

| Модель | PR-AUC | Precision@300 | Recall@300 | Чистый эффект @300 |
|---|---:|---:|---:|---:|
| Правила (новый телефон или транзит) | 0,355 | 0,37 | 0,42 | 59,2 млн ₽ |
| Логистическая регрессия | 0,747 | 0,71 | 0,81 | 82,3 млн ₽ |
| Градиентный бустинг | **0,800** | **0,81** | **0,93** | **89,4 млн ₽** |

- Бустинг даёт на 51% больше чистого эффекта, чем правила, при той же нагрузке на команду. Доля верных алертов растёт с 37% до 81%.
- Оптимум по деньгам приходится примерно на 566 алертов, а команда разбирает 300. Расширение проверки добавило бы около 1 млн ₽: это аргумент в разговоре о найме или автоматизации разбора.
- Хуже всего ловятся «продвинутые» дропперы: recall 0,89 против 0,96 у простых.
- Среди 300 алертов 56 ложных: 44 обычных клиента, 10 студентов, 2 продавца. Таким клиентам лучше показать мягкий сценарий («подтвердите операцию»), чем блокировать.

Самые важные признаки: число уникальных отправителей, сумма входящих, доля круглых сумм, доля вывода наличными и скорость вывода. Это совпадает с тем, как дропперские схемы описывает ЦБ.

## Что дальше

1. **Лестница реакций вместо бинарной блокировки:** низкий скор — ничего; средний — push и период охлаждения; высокий — ручная проверка и приостановка по 161-ФЗ.
2. **A/B этой лестницы:** основная метрика — потери от мошенничества на 1 000 клиентов, guardrails — доля успешных переводов, обращения в поддержку, NPS.
3. **Мониторинг:** мошенники адаптируются, поэтому раз в неделю нужно считать PSI признаков и precision на свежих подтверждениях.
4. **Графовые признаки:** цепочки «дроппер → дроппер» видны в данных, но в модель пока не заложены.

## Запуск

Нужен Python 3.10+.

**macOS / Linux**
```bash
git clone https://github.com/antonshkelll/drophunter-antifraud.git
cd drophunter-antifraud
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python src/generate_data.py   # ~5 сек, данные в data/
python src/train.py           # ~15 сек, метрики и графики в reports/
pytest -q
```

**Windows (PowerShell)**
```powershell
git clone https://github.com/antonshkelll/drophunter-antifraud.git
cd drophunter-antifraud
py -m venv .venv; .venv\Scripts\Activate.ps1
pip install -r requirements.txt
python src/generate_data.py
python src/train.py
```

Бизнес-допущения (стоимость проверки и ложной блокировки, мощность команды) заданы константами в начале [`src/train.py`](src/train.py).

## Ограничения

- Данные синтетические: проект показывает подход, а не качество на реальном банке.
- В жизни разметка приходит с задержкой (жалоба жертвы через дни или недели), и в проде это нужно учитывать.
- Стоимость ложной блокировки (2 100 ₽) — допущение, и обсуждать с бизнесом нужно именно его.
